# QueryGateway v0.2.0 — Security & Performance Hardening Plan

## Goal

Ship v0.2.0: close the remaining security gaps (rate limiting, scheduler persistence, edge hardening, audit retention) and the biggest performance costs (per-request Oracle connection setup, per-request bcrypt/API-key cost, per-request model rebuilds, single-bundle frontend), plus small aligned features. Multi-database support (docs/phase2.md) is explicitly deferred to v0.3.0.

## Resolved Scope Decisions

| Decision | Outcome |
|---|---|
| v0.2.0 feature scope | Hardening + performance + small features only; multi-DB deferred to v0.3.0 |
| API key verification cost | Keep bcrypt storage (no convention change); add bounded in-memory verified-key cache with explicit invalidation on rotation/update/delete |
| Rate limiting tech | Custom pure-ASGI middleware, in-memory sliding window, no new dependency (respects SECURITY.md §4 supply-chain directive) |
| Scheduler persistence | Re-register active schedules from DB at startup; keep in-memory job store and the documented single-replica constraint (production_deployment.md gap #10) |

## Findings (with evidence)

### Security

| ID | Severity | Finding | Evidence |
|---|---|---|---|
| S1 | High | No rate limiting / brute-force protection anywhere. `/api/v1/auth/login` unthrottled (single admin account), per-endpoint auth checks (bearer/basic/api_key) unthrottled, data endpoints unthrottled → credential attacks and Oracle DoS possible | `backend/app/routers/auth.py:33`, `backend/app/services/data.py:179-255`; no limiter exists in `app/middleware.py` or `app/main.py` |
| S2 | High | Oracle executor opens a fresh connection per query; `oracledb.connect()` has no connect timeout, so an unreachable listener can hang a worker thread beyond `query_timeout` (which is set only after connect) | `backend/app/sql/executor.py:52-54` |
| S3 | High | Scheduler jobs lost on restart: APScheduler uses the in-memory job store and `start_scheduler()` never re-registers rows from `schedules`; after any restart/deploy all snapshot refreshes silently stop until an admin edits each schedule | `backend/app/services/scheduler.py:210-228`, `backend/app/services/schedule.py:106-113` (jobs added only on create/update/resume) |
| S4 | Medium | nginx edge lacks security headers (HSTS, X-Content-Type-Options, X-Frame-Options, CSP, Referrer-Policy), compression, explicit body-size cap, and `Cache-Control` for API responses; no TLS enforcement story in compose | `docker/nginx.conf` (29 lines, proxy + SPA fallback only); production_deployment.md gap #4 |
| S5 | Medium | No retention for `access_logs` and `job_runs` — unbounded table growth (snapshots already have `snapshot_retention_count`) | `backend/app/services/scheduler.py:137-148` (retention exists for snapshots only) |
| S6 | Low | No audit-friendly listing of public (`allow_unauthenticated`) endpoints to support the go-live audit in production_deployment.md gap #7 | `backend/app/services/data.py:113-134` |

### Performance

| ID | Impact | Finding | Evidence |
|---|---|---|---|
| P1 | High | One TCP+auth handshake to Oracle per data request; stored `pool_min`/`pool_max`/`pool_timeout` columns exist but are never used | `backend/app/models/connection.py:43-45`, `backend/app/sql/executor.py:52` |
| P2 | High | bcrypt cost-12 verification on every api_key/basic-authenticated data request (~200–300 ms CPU each); generated API keys already carry ~192 bits of entropy | `backend/app/auth/hashing.py:41`, `backend/app/services/auth_method.py:339-346` |
| P3 | Medium | `build_param_model()` runs `pydantic.create_model` on every live data request | `backend/app/services/data.py:370`, `backend/app/sql/param_models.py:103` |
| P4 | Medium | Every data request performs 3+ Postgres round-trips (endpoint by path, auth method, connection) plus one access-log insert+commit on the critical path, with zero caching | `backend/app/services/data.py:109-112,314`, `backend/app/services/access_log.py:103-121` |
| P5 | Medium | Frontend ships a single bundle — CodeMirror (~large) loaded for every page; no `React.lazy`/route splitting; no axios timeout; no compression or cache headers for immutable snapshots | `frontend/src/App.tsx` (static imports), `frontend/src/lib/api.ts`, `docker/nginx.conf` |

## Implementation Plan (ordered)

### Workstream A — Backend security (must-have)

**A1. Rate limiting middleware (S1)**
- Add `RateLimitMiddleware` as a pure-ASGI middleware (NOT `BaseHTTPMiddleware` — preserves the asyncpg task-binding constraint documented in `app/middleware.py:11-14`).
- In-memory sliding-window counters keyed by `(client_ip, scope)`. Client IP from `request.client` (already correct: nginx overwrites `X-Forwarded-For` with `$remote_addr`, uvicorn trusts only `10.31.0.0/24`).
- Bounded state: maximum distinct keys (configurable, e.g. 10k), periodic expiry sweep of idle windows, and an explicit overflow policy (evict the oldest window; never evict the global auth budget). Prevents an attacker from exhausting memory with synthetic client IPs.
- Scopes: `auth` (`/api/v1/auth/*`, strict default e.g. 10 req/min/IP), `data` (`/api/v1/data/*`, configurable), `admin` (everything else, lenient). Health probes excluded.
- Bounded global authentication failure budget (e.g. N failed `/api/v1/auth/login` attempts per minute across all client IPs) in addition to the per-IP limits — distributed attempts against the single admin account cannot bypass throttling by spreading across IPs. Keyed by username+scope (not client IP), with the same expiry sweep and overflow policy.
- Return `429` with `Retry-After` header; emit structured `rate_limited` log with the mandatory field set (request_id, user, endpoint, status, method, client_ip, duration_ms).
- Config via Pydantic Settings (`RATE_LIMIT_*` env vars) with sane defaults and an enable/disable flag.
- Document single-process limitation alongside the existing single-replica scheduler constraint.
- Register outermost-first ordering carefully: limiter must run after CORS for preflights but before route handling; verify CORS headers still apply to 429 responses.

**A2. Scheduler restart persistence (S3)**
- After `start_scheduler()` in lifespan, load all active `Schedule` rows via `AsyncSessionLocal` and call `add_schedule_job` for each; log `scheduler_jobs_restored` with count.
- Restore in exactly one process: guard job registration/execution with a single-process flag or a Postgres advisory lock, because every restored job runs Oracle queries. Do NOT follow the current `docs/deployment.md` guidance (`--workers 4` at L86/L93, Kubernetes `replicas: 2+` at L153) until distributed coordination exists — see D3, which replaces those recommendations.
- Failure to restore must not crash startup, but must be visible: expose a degraded state on the readiness probe and log `scheduler_restore_failed` with the failing schedule ids so operators can alert on it.
- Startup test: exactly one APScheduler job per active schedule after restore; a multi-process simulation proves no duplicate job registration/execution.

**A3. Public-endpoint audit surface (S6)**
- Add list of active endpoints with `allow_unauthenticated=true` (id, path, name, updated_at) to the admin-gated health dashboard response.

**A4. Audit retention (S5)**
- New seeded settings: `access_log_retention_days` (default 90), `job_run_retention_days` (default 30) — follow the `snapshot_retention_count` pattern in `SettingsRepository`.
- Seed via a new Alembic data migration (new revision; never edit applied migrations).
- Daily cleanup job registered at scheduler startup (runs `DELETE ... WHERE created_at < now() - retention` in batches); also run once at startup if last cleanup unknown.

**A5. Edge hardening (S4)**
- `docker/nginx.conf`: add `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, CSP for the SPA, `gzip on` for JSON/JS/CSS, explicit `client_max_body_size 1m`, long-lived immutable caching for hashed static assets.
- CSP details: no inline scripts exist, but CodeMirror injects runtime `<style>` elements via `style-mod` (`frontend/package-lock.json`), which cannot carry hashes/nonces — so keep `script-src 'self'` strict and use `style-src 'self' 'unsafe-inline'` (documented trade-off; verify the wizard renders after applying).
- `Cache-Control: no-store` applies to admin API responses (`/api/v1/admin/*` and `/api/v1/auth/*`) only — NOT to `/api/v1/data/*` snapshot responses, which carry the ETag/304 contract from B5 (a blanket `/api/` no-store would defeat revalidation).
- HSTS header documented as an add-on at the TLS layer (production_deployment.md gap #4) — nginx listens on 80 today, so HSTS belongs where TLS terminates; document in deployment.md.

### Workstream B — Backend performance (must-have)

**B1. Oracle connection pooling (P1, S2)**
- Add a process-level pool registry keyed by connection id in `app/sql/executor.py`: lazily create `oracledb.create_pool(min=pool_min, max=pool_max, getmode=POOL_GETMODE_TIMEDWAIT, wait_timeout=pool_timeout*1000, timeout=300, ...)` per connection. `pool_timeout` is documented as "Seconds to wait for a pool slot" (`schemas/connection.py:33`) — that maps to the acquisition wait via `getmode`/`wait_timeout`, NOT to `create_pool(timeout=...)`, which controls idle connection lifetime (keep an idle `timeout` for reaping, e.g. 300 s).
- Set a connect timeout (thin mode `tcp_connect_timeout`; degrade to direct `oracledb.connect` with the same timeout if pool creation fails) so unreachable listeners cannot hang worker threads.
- Invalidate/destroy pools on connection update/delete and on credential rotation: expose `invalidate_pool(connection_id)` called from `ConnectionService` update/delete paths.
- Pool lifecycle: `invalidate_pool` retires gracefully — stop handing out new connections while letting in-flight queries drain, then `close()` the pool. Close all pools during lifespan shutdown (`app/main.py` teardown) so no Oracle sockets leak at exit.
- Pools are thread-safe in python-oracledb; creation inside `anyio.to_thread.run_sync` is fine. Handle thick mode (client already initialized once in lifespan).
- Connection test (`services/connection.py`) keeps using a direct one-off connect.

**B2. Verified API-key cache (P2)**
- Add a bounded in-memory cache in `app/services/auth_method.py` (or a small `app/auth/key_cache.py`): key = `(auth_method_id, sha256(presented_key))`, value = verified bool, TTL ~60 s, max size ~1024, `hmac.compare_digest` for internal lookups.
- Keep bcrypt as the source of truth: cache miss → `verify_password` → populate on success only (never cache failures, so brute force gains nothing).
- Invalidation contract: drop all entries for an auth method whenever anything verification-affecting changes — `config_json` (secrets, expiry), `method_type`, credentials, or `is_active` — i.e. in `rotate_credentials`, `update_auth_method`, `delete_auth_method` (and any future mutator of these fields).
- Invalidation must be post-commit: the routers commit after the service calls (`auth_methods.py:146,163,207`), so a concurrent request between a service mutation and the commit could otherwise read the old hash and repopulate a success entry that outlives the rotation. Apply invalidation after `db.commit()` (post-commit hook, or an invalidation signal the router fires).
- Process-local invalidation is sufficient under the single-process deployment constraint; cross-process consistency (e.g. a shared cache) is out of scope until multi-process deployments are supported.
- Basic-auth (human passwords) stays uncached — bcrypt there is intentional.

**B3. Param model cache (P3)**
- Cache `build_param_model` results in an LRU keyed by `(endpoint_id, updated_at)` (or a hash of the schema dict); used by `DataService._coerce_params`.

**B4. Endpoint/auth/connection resolution cache (P4, partial)**
- Fail-closed design: authorization-bearing inputs are NEVER positively cached. `endpoint.is_active`, `endpoint.auth_method_id`, `endpoint.allow_unauthenticated`, auth-method `config_json`/`method_type`/`is_active`, and connection active state are always read from the DB on the request path. A positive cache could outlive a mutation (TTL + invalidation is racy, not authoritative) and would break the M1 default-deny guarantee of `data.py:111-134`.
- Positive caching is limited to authorization-irrelevant data: the param model (B3) and non-auth connection metadata (DSN fields, credential envelope) where a short TTL cannot change an allow/deny outcome. No `updated_at`-keyed shortcut for the security-sensitive fields above.
- Access-log writes stay synchronous with a dedicated session — auditability outranks the one extra round-trip in v0.2.0 (batched writes recorded as future work, see Out of Scope).

**B5. Snapshot response caching headers (P5, cheap win)**
- Add `ETag: <snapshot.id>` and `Cache-Control: private, max-age=0, must-revalidate` on snapshot responses; honor `If-None-Match` → 304 in `_serve_snapshot`. Because A5 applies `no-store` only to admin/auth routes, snapshot ETags pass through nginx unchanged — verify the effective response headers through the nginx edge in the e2e check.

## Task Order & Dependencies

1. A2 (scheduler restore) — standalone, unlocks A4 cleanup job.
2. A4 (retention) — depends on A2 scheduler being trustworthy.
3. B1 (pooling) — standalone; touches executor + connection service only.
4. B2 (key cache) — standalone; touches auth_method service only.
5. B3 + B4 (caches) — do B3 first (trivial), B4 after A1 so invalidation hooks and rate limiter don't conflict.
6. A1 (rate limiter) — before B4 so middleware ordering is settled.
7. A3, A5, B5, C1, C2 — independent, parallelizable.
8. D1–D3 last.

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Stale authorization served from a positive cache (security regression of M1 default-deny) | Authorization-bearing inputs are never positively cached (B4) — always read from the DB — so the default-deny path is fail-closed by construction; add regression tests mirroring `test_public_endpoint.py` scenarios (delete auth method → immediate 401, not cached 200) |
| oracledb pool lifecycle issues across worker threads / thick mode | Pool registry guarded by a lock; graceful retirement (stop new acquisitions, drain in-flight, then close) plus pool close on lifespan shutdown; graceful fallback to direct connect; integration-marked test with live Oracle, unit tests with mocks otherwise |
| In-memory limiter resets on restart / useless beyond one replica | Bounded state with expiry sweep and documented overflow policy; single-process constraint documented; nginx-level limiting documented as the multi-replica path |
| Key cache weakens rotation immediacy | Post-commit invalidation on every verification-affecting change (rotate/update/delete); test asserts a rotated key is rejected on the very next request |
| Scheduler restore doubles jobs if `replace_existing` semantics change | `add_schedule_job` already uses `replace_existing=True`; restore is single-process guarded; startup test asserts exactly one APScheduler job per active schedule |
| Rate limiter blocks legitimate health checks / orchestrators | Health probe paths excluded from limiting; bounded-state overflow never evicts the global auth budget; test |

## Out of Scope (recorded for v0.3+)

- Multi-database support (docs/phase2.md) — v0.3.0.
- Write endpoints, consumer OpenAPI/Postman export, RBAC, GraphQL (README roadmap).
- Batched/async access-log writes (kept synchronous for audit integrity in v0.2.0).
- JWT revocation lists for admin tokens (bounded by 60-min TTL; documented trade-off stands).
- localStorage → httpOnly cookie token migration (documented trade-off in `frontend/src/lib/auth.tsx` stands until user-supplied HTML rendering exists).
- Image signing (cosign) and branch protection — repo-admin items, tracked in security_checklist.md #63–#64.
